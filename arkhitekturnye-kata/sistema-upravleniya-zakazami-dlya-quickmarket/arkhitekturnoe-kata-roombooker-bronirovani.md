*  {% colwidth=[366] %}

   ⏱️Скорость изменений бизнес-требований

*  {% colwidth=[458] %}

   Высокая: ранняя стадия продукта, гипотезы (форматы уроков, логика тестов, правила выдачи сертификата) будут меняться каждые несколько недель. Границы модулей ещё не устоялись -> нужна архитектура, где изменение контракта между модулями -- это рефакторинг в одной кодовой базе, а не согласование версий API между сервисами

---

*  {% colwidth=[366] %}

   👥 Количество независимых команд

*  {% colwidth=[458] %}

   Одна команда (по факту 3–7 человек). По закону Конвея одна команда естественно производит один деплой-юнит. Дробление на сервисы при одной команде даёт накладные расходы без выигрыша в автономии

---

*  {% colwidth=[366] %}

   🏛️ Legacy-ограничения

*  {% colwidth=[458] %}

   Отсутствуют: greenfield-проект, интеграций с унаследованными системами нет. Единственные внешние зависимости -- платёжный провайдер, почта/уведомления и хранилище видео (S3-совместимое + CDN). Свобода выбора стека полная

---

*  {% colwidth=[366] %}

   🛡️ Требования к SLA / отказоустойчивости

*  {% colwidth=[458] %}

   Умеренные: сервис не финансовый и не медицинский, простой в 15–30 минут не критичен. Целевой SLA \~99,5%, RPO/RTO -- часы. Критичный сценарий один -- итоговый тест: недопустима потеря ответов и прогресса, поэтому ответы сохраняются пошагово (не одним батчем в конце). Достаточно резервирования БД + бэкапы, кластеризация не нужна

---

*  {% colwidth=[366] %}

   💰 Бюджет и сроки

*  {% colwidth=[458] %}

   Бюджет стартапа, приоритет -- time-to-market MVP. Монолит: один деплой-пайплайн, одна БД, один инстанс + реплика. Микросервисы потребовали бы Kubernetes, service mesh, distributed tracing, отдельных БД -- это месяцы работы и кратно дороже в инфраструктуре и поддержке

---

*  {% colwidth=[366] %}

   ⚙️Зрелость DevOps-культуры команды

*  {% colwidth=[458] %}

   Низкая/средняя: есть опыт веб-разработки, нет опыта высоконагруженных и распределённых систем. Нет отлаженных практик мониторинга, распределённой трассировки, on-call. Эксплуатация 6–8 сервисов при таком уровне зрелости -- главный источник риска. Монолит позволяет наращивать DevOps-практики постепенно

{% /table %}

## 🚩 4. Главный риск выбранного решения

-  При росте и развитии проекта появятся ошибки. Границы между модулями держатся только на дисциплине команды. Первый прямой вызов чужого репозитория и первый `JOIN` между схемами сегодня ничего не ломают и экономят разработчику время, но через год монолит срастётся внутри и перестанет разрезаться на модули. У команды нет опыта распределённых систем
